# golang-core v0.8.24 patch (PIX-2606, ai proxy stream)

Changes on top of v0.8.24 needed by the streaming proxy of the api (`/api/1.0/ai/...`) and by the
`stream: true` routes of gogen. The branch `PIX-2606-ai-proxy-stream` holds them; the api uses it through a
`replace` until a release is cut.

## 1. Request logger does not drain a streamed body

`http/request_log_handler.go`: `response_bytes` was `len(ctx.Response.Body())`. For a body set with
`SetBodyStreamWriter`, `Body()` reads the whole stream into memory, so the handler chain returned only after
the stream had ended and the client received everything in one piece at the end (measured on the prototype: an
answer of 10 s arrived after 14.5 s in three chunks).

Now a streamed body is not read: `response_bytes` is its declared length when it has one
(`SetBodyStream(reader, size)` with `size >= 0`, read from `Content-Length`) and `StreamedResponseBytes` (`-1`)
for a stream of an unknown length (`SetBodyStreamWriter`, a negative size); a buffered body is measured as before.

## 2. `http.StreamResponse` and `http.HandleStream`

`http/stream_response.go`, the response of a handler whose body is written while it is sent:

- `StreamWriter` - `func(*bufio.Writer)`, the type `SetBodyStreamWriter` takes;
- `StreamResponse` - status code, headers and the writer; `NewStreamResponse(status, headers, writer)`, a zero
  status means 200;
- `HandleStream(ctx, response)` - sets the status and the headers and hands the writer to fasthttp; a nil
  response or writer is a 500 (`ErrNoStreamWriter`). `Writer()` of a nil `*StreamResponseImpl` is nil, so a
  typed nil response in the interface is the same 500 and not a panic.

gogen emits `http.HandleStream(ctx, response)` for a `stream: true` operation, whose controller returns
`http.StreamResponse`.

fasthttp runs the writer on a goroutine of its own as soon as it is handed over and may release the request
while the writer still runs (the client is gone): the writer must not use the request context.

## 3. `http.ErrRequestEntityTooLarge`

`http/error.go`, `http/response_renderer.go`: a new error rendered with 413, for a body limit stricter than
the server one (the ai proxy refuses bodies above its own limit). The api's proto renderer maps 413 to
`ERROR_BAD_REQUEST`.

## 4. `http_client.Client.DoStream`

`http_client/do_stream.go`: `DoStream(ctx, method, uri, opts...) (StreamResponse, error)` sends a request of
any method (a `POST` with a body) and returns the body as an `io.ReadCloser` read while the server writes it.

- The response is returned for every status code; the caller reads the status and the error body itself (a
  proxy passes a 429 with its `Retry-After` on). `GetStream` keeps turning a non-2xx status into an error.
- `Timeout()` bounds the wait for the response headers. Connecting and the TLS handshake have a bound of their
  own, `StreamConnectTimeout` (30s), or `Timeout()` when it is shorter: the header timeout of a stream client is
  minutes (a model thinking before its first byte), a host that does not accept the connection is known to be
  down much sooner. The body has no deadline; canceling `ctx` aborts the request and closes the connection, also
  while the body is read.
- No retries and no circuit breaker: a stream can not be replayed.
- Request options, base headers, the request id, query params, form data and redirects follow the existing
  rules; the log line is the one of `GetStream` with the method.

It is built on `net/http`, not fasthttp: fasthttp applies one read deadline to the headers and the whole body
(a stream is cut at the timeout or has no header timeout at all) and can not abort a request in flight. The
transport is configured from the same `Config`: TLS, `MaxConnsPerHost`, `MaxIdleConnDuration`, HTTP/2 allowed,
compression off (the body comes as the server sent it, as with fasthttp). `Client` gains the method, the mock
is regenerated.

The transport gets a copy of the TLS config (`tlsConfig.Clone()`), not the one of the fasthttp client: net/http
adds `h2` to `NextProtos` of the config on its first request (also a data race with fasthttp reading it), after
which fasthttp offers `h2` over ALPN to every new host, gets an HTTP/2 answer and fails with "the server closed
connection before returning the first response byte".

## 5. `json.Decoder`, `json.NewDecoder`, `json.Token`, `json.Delim`

`json/json.go` re-exports the streaming decoder of goccy/go-json. `Unmarshal` can not tell how a member name was
written: into a struct it matches names ignoring case and keeps the last duplicate, into a map it keeps the last
duplicate too. The ai proxy of the api checks the `model` of a body it passes on byte for byte, so it walks the
top level object with `Token` and refuses a checked member that is repeated or written in another case (the
provider could read another one than the proxy).

## 6. Preloader data race

`preloader/preloader.go`: `Value` read `currentValue` and `lastRefreshAt` without a lock while `Refresh` wrote
them under the mutex, a data race in every preloader (`go test -race` reports it). When the value expired, every
caller that came in meanwhile waited for the mutex and then called the loader again, one after another.

Now the value and the refresh time are guarded by an `RWMutex` of their own; the loader calls stay serialized by
the old mutex and run without holding the state lock, so readers of a fresh value never wait for a load. `Value`
of an expired value checks it again after taking the loader mutex and loads only if nobody refreshed it
meanwhile. `Refresh` always loads, as before; errors and the default value on a failed load are unchanged.

## Tests

- `http/stream_response_test.go`: through `RequestLogHandler` on a real server the first chunk arrives while the
  writer still waits (the old logger fails this test), status and headers are sent, a closed client fails the
  writer, the size of a streamed body is read without draining it.
- `http/render_test.go`: 413 mapping.
- `http_client/do_stream_test.go`: POST body, headers and query reach the server, chunks are readable before
  the end, an error status comes with its body, the timeout bounds the headers only, the connect timeout cuts a
  TLS handshake the server never answers (header timeout of a minute), the connect timeout is the default or the
  shorter header timeout, a canceled context aborts the body and before the headers, redirects follow the config,
  form data and body conflict, a TLS config (`insecure_skip_verify`) with an HTTP/2 server: after `DoStream` over
  h2 a `Get` of the fasthttp client to another host goes over HTTP/1.1 (fails with the shared config).
- `http/stream_response_test.go`: a typed nil response is a 500 (a panic before).
- `http/stream_response_test.go` (`TestResponseBytes`): a stream of a known length is logged with it, one of an
  unknown length with `-1`.
- `preloader/preloader_test.go`: 20 concurrent `Value` calls of an expired value call the loader once (12 times
  before the fix); concurrent `Value`, `LastRefreshAt` and `Refresh` are clean under `-race` (5 races before).
- `json/json_test.go`: the decoder walks an object member by member with escaped names decoded and duplicates
  and case variants kept.

`go test ./...` is green. `make lint` does not start with the local golangci-lint 2.12.2 (`exhaustruct_v5` is
unknown to it); with that one line removed from a copy of the config the whole repository has 0 issues.

## Noticed, not changed

`GetStream` closes the body with `ReleaseResponse`, which closes the fasthttp body stream with a nil error. For a
body that was not read to the end fasthttp then returns the connection to the pool with the rest of the body
still unread, and the next request on that connection may read it as its response. Callers that always read to
EOF are not affected.
